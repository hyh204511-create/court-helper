# 企业微信群机器人 Webhook 推送模块规格

## 1. 目标

查询结果对应截图成功持久化后，服务端自动向企业微信群机器人推送一次通知。通知包含对应证据截图、原告/被告名称、案件结果内容，并同时 `@业务员` 与 `@助理`；失败记录只允许后台人工重试。

## 2. 配置与敏感信息

- Webhook 仅从服务端环境变量 `WECOM_WEBHOOK_URL` 读取，不进入数据库、浏览器、Git、Obsidian、响应正文或日志。
- URL 必须为 HTTPS，主机必须精确等于 `qyapi.weixin.qq.com`，路径必须为 `/cgi-bin/webhook/send`，且必须含非空 `key` 参数；不允许请求任意 URL。
- 业务员和助理使用企业微信成员 UserID，按平台账号绑定并持久化在 `platform_accounts`；后台普通列表仅返回是否已配置，只有管理员编辑接口可写入，接口和日志不回显完整 UserID。
- 旧版手机号绑定只作为迁移兼容数据保留，通知服务、后台接口和表单不得读取、回显或发送旧手机号；升级后必须由管理员重新配置两名成员的企业微信 UserID。
- 真实案件名称、案号、结果内容和截图仅发送到用户配置并主动触发的目标企业微信群；自动化测试只能使用脱敏合成数据。

## 3. 入口与权限

- 后台平台账号管理页为管理员提供“业务员企业微信 UserID”“助理企业微信 UserID”绑定字段；两个字段必须同时配置或同时清空。
- 截图上传接口完成案件与截图落库后，必须先成功创建或确认幂等通知台账再返回成功，防止截图已成功但后台没有通知记录；新通知必须在同一次数据库写入中显式保存初始状态 `pending`，不得依赖表字段默认值。实际网络推送继续异步执行，推送失败只更新通知记录为 `failed`。通知台账创建失败时上传请求返回失败，客户端可凭同一截图幂等重试并补建台账。
- 上述异步发送不等于一键任务成功：`QUERY_ALL_EXPORT` 回写终态时，服务器必须再次确认本次每条终态证据对应的通知记录已经达到 `sent`；`pending`、`sending` 或 `failed` 均按 `EVIDENCE_NOT_CLOSED` 转人工，禁止显示“成功/报表已上传服务器”。
- 人工重试接口为 `POST /wecom-notifications/:id/retry`，只接受后台 Cookie 会话与有效 CSRF；扩展 Bearer、匿名请求和越权访问均拒绝。
- Webhook 未配置时页面可保留入口，但提交返回稳定错误 `WECOM_NOT_CONFIGURED`，不得把配置值返回客户端。

## 4. 消息内容与顺序

1. 仅 `立案成功`、`强执成功`、`已驳回` 三种终态进入自动推送；从服务端案件记录读取平台账号、原告、被告、案件类型、状态、案号、驳回原因和查询时间，禁止由客户端提交或覆盖这些业务字段。
2. 按结果选择截图：`已驳回` 使用 `reject`；立案成功使用 `success`；强执成功使用 `enforcement_success`。没有对应截图时停止并返回 `WECOM_SCREENSHOT_MISSING`，不发送无图通知。
3. 图片从私有对象存储读取，转换为企业微信 `image` 消息要求的 Base64 与 MD5。原始图片超过企业微信 2 MiB 限制时返回 `WECOM_IMAGE_TOO_LARGE`。
4. 先发送图片，再发送一条 `text` 消息。文本至少包含案件类型、原告、被告、结果、案号（存在时）、驳回内容（存在时）和查询时间（存在时）。`mentioned_list` 同时包含业务员与助理的企业微信成员 UserID，去重但不得使用 `@all`；不得再发送 `mentioned_mobile_list`。
5. 企业微信返回 HTTP 非成功、非 JSON、`errcode != 0` 或网络失败时记录稳定错误码 `WECOM_DELIVERY_FAILED`；不得持久化或向客户端、日志透传 Webhook、响应正文、UserID 或案件明文。图片成功而文本失败属于失败，操作员核实群内情况后可人工重试。
6. 通知唯一键为 `(case_id, result_status)`。首次终态截图上传通过原子创建取得发送权；重复同步、相同截图重传、服务重启或并发上传均不得再次自动发送。状态将来从一个终态变为另一个终态时，允许按新结果产生一条新通知。
7. 发送前必须再次校验案件当前结果仍等于通知结果、截图仍属于该案件且截图类型与当前结果一致；任一来源已变化时以 `WECOM_SOURCE_CHANGED` 失败，不得混用旧截图与新结果文本。
8. 通知记录只持久化案件 ID、平台账号 ID、结果状态、`pending/sending/sent/failed`、安全错误码、尝试次数及时间；不保存消息正文、截图 Base64、UserID、Webhook 或企业微信响应。

## 5. 输入校验与节流

- 平台账号的两个企业微信成员 UserID 必须同时填写或同时清空；填写时去除首尾空白，长度为 1–64 个字符，不得包含控制字符，也不得等于企业微信保留值 `@all`。
- Webhook 未配置、联系人未配置、案件非三种终态或对应截图缺失时不访问企业微信；联系人未配置时创建 `failed/CONTACTS_NOT_CONFIGURED` 记录，供配置后人工重试。
- 自动推送每条通知最多尝试 1 次；没有后台定时器、队列轮询或自动重试。每次人工点击重试只增加 1 次尝试并重新发送一次，按钮提交期间禁用。

## 6. 范围外

- 企业微信自建应用、智能机器人插件、群聊管理、通讯录查询、UserID 自动发现、通过手机号 @、失败自动重试、定时批量推送。
- 修改法院状态映射、截图采集规则、案件数据结构、报表导出格式。

## 7. 验收闸门

- TDD 覆盖迁移回滚、旧手机号迁移后不再启用联系人、PostgreSQL 通知仓库显式写入 `pending`、UserID 成对绑定与脱敏、UserID 校验、三种终态触发、非终态跳过、并发唯一去重、重启幂等、Base64/MD5、`mentioned_list` 双人 @ 且无 `mentioned_mobile_list`、失败记录、无自动重试、人工重试权限和企业微信错误脱敏。
- `npm run server:build` 与 `npm test` 通过。
- 仓库敏感信息扫描确认无真实 Webhook key、手机号、企业微信 UserID、案件名称、结果截图或响应正文。
